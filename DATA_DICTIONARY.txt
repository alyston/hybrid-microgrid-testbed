DATA DICTIONARY AND REANALYSIS CONVENTIONS
All exports are CSV compressed with gzip. Missing fields mean not applicable/unavailable; they are not measurements of zero. Original row order is retained. Original source files are identified by SHA-256 in nominal_evidence/PROVENANCE.json.

*_packets.csv.gz: one row per complete original PCAP record, including nonindustrial packets. frame is the 1-based record number; relative_ns is the integer capture timestamp minus the first complete packet timestamp. captured_bytes and wire_bytes retain capture/original record lengths. transport is the parsed transport or OTHER. src/dst are stable host labels within that capture only; src_port/dst_port are original transport ports. seq/ack, flags, tcp_window and payload_bytes retain TCP metadata. mb_tid, mb_uid and mb_fc are the Modbus transaction, unit and function fields. eip_cmd is the encapsulation command; eip_context is a within-capture pseudonym preserving equality of sender contexts. payload_sha256 hashes the full TCP payload for industrial packets; no payload value is distributed.
The parser supports the link types explicitly listed in packet_fields.py, unfragmented IPv4 and basic IPv6 without extension-header traversal. It does not reassemble TCP streams or split multiple application messages in one TCP payload. In these selected captures, no industrial payload packet failed the header decoder; this is not a general parser-accuracy guarantee. Matching uses a direction-normalized connection, protocol identifier and FIFO order. The PCAP sequence-repeat statistic follows the archived high-watermark rule; it is not an independent estimate of network loss. Modbus payload identity and cross-segment correspondence can also be checked against modbus_matched_operations.csv.
One EIP LD0 capture ends with a 16-byte packet-record header whose 169-byte body is absent. It is excluded as an incomplete record, and its extent is declared in PROVENANCE.json. This is distinct from the two final complete Modbus request packets without replies. No packet or transaction is synthesized.

*_router.csv.gz: source_row is the original 1-based CSV line including its header. relative_ns is the original log timestamp relative to that file's first row. event_type, direction and device identify event boundaries. inter_event_ms, jitter_ms, duration_ms and duration_jitter_ms are the original logged durations. payload_bytes, protocol, port, interface_name and transport identify the exchange type without addresses. memory_age_ms, rx_age_ms and memory_update_age_ms are logged ages. rx_version, tx_version and cycle_index retain counters. has_new_tx, should_send, send_attempted, send_success, retry_attempts, completion_state and rx_fresh retain event state. rx_protocol, unit_id, area, function_code, is_write, addr and quantity preserve protocol/mapping fields; addr is a Modbus register offset, not a network address. status is retained. error_present/last_error_present preserve whether removed free-text error fields were nonempty. Absolute update timestamps, peer/client addresses and free-form source/error fields are removed.
Router event counts include initial rows. Interval statistics use positive inter_event_ms values, excluding each stream's zero-valued initialization record, not an arbitrary warm-up. Thus interval sample counts can be six fewer than event counts. Physical input means event_type=physical_io AND direction=eth0_in_from_opal; command-cycle means event_type=command_cycle; controller-side request means event_type=modbus_request. In the EIP acquisition, this last event is an internal Modbus interface exchange, not the native controller EtherNet/IP transaction. No subtraction of separate device clocks is used.

*_EMS_application.csv.gz: source_row and relative_ns have the same conventions. MB timestamps denote request start, as shown by Timestamp:start in the archived EMS code and the packet correspondence. duration_ms is elapsed local routing duration. device_name, unit_id, transaction_id, function_code, req_bytes, resp_bytes and status retain operation metadata. EIP loop_type, loop_index, device, protocol, function_code, operation, direction, target, status and duration_ms retain the original application fields. operation is WRITE_STATUS_FEEDBACK, READ_COM_REF or SCAN_SUMMARY. Scan columns scan_write_ms, scan_latency_ms, scan_read_ms, scan_total_ms, budget_ms, overrun and overrun_by_ms are the original summary fields. The scan interval is not an electrical actuation measurement. Details/error text is removed; error_present is retained.

Statistics: milliseconds; linear quantiles at (n-1)*p; population standard deviation; all completed operations and all EIP scan records retained, including stale_write and the longest scan. Reconstructed MB sweeps require the complete ordered six-endpoint sequence separately for FC04/FC16. Their duration is last request start plus LAST request duration minus first request start. Gaps run from that completion to the next POI write start. Complete cycles run between consecutive POI write starts. See MODBUS_SWEEP_CORRECTION.txt.
Packet Table 12 uses all complete capture packets in its packet-count column. Industrial goodput sums TCP payload for the industrial flows over the whole capture duration; the EIP capture also contains internal Modbus. Its native RTT uses TCP/44818 only. Table 13 chooses each device capture's most populated UDP flow on a port in 23000-23099, computes successive intervals within that capture and divides payload bytes by that flow's first-to-last packet interval. These observations do not calibrate NS-3 or the complete electrical loop.
